# 需求

负责：要做什么、优先级、所属阶段、验收标准、行为规则、已否定方案。
上游：两份原始需求文件只读（`优化与前言.txt`、`流程与要求.txt`）。
改动影响：需求变化会影响 `docs/architecture.md`、`TODO.md`；安全相关条目同时影响 `docs/security.md`。

## 0. 项目目标

一个 Telegram 群宠 Bot：多群共用人设，数据与工作区严格隔离；只在值得说话时说话；
能用工具（计算、搜索、文件、贴纸、沙箱代码）；权限与安全边界由程序裁决；成本可记账、可限额。

### F1 接入与隔离（阶段 1）

| 编号 | 需求 | 优先级 | 验收 |

| F1.1 | long polling 单进程接收群消息 | P0 | 群里发消息，日志可见且能回复 |

| 编号 | 需求 | 优先级 | 验收 |

## 2. 行为规则（产品层）

本节是发言行为的唯一权威来源；人格与语气见 `docs/persona.md`。

### 2.1 群聊发言规则

1. 不要求用户 @ 它：只要消息符合当前发言规则，就可以主动回复（阶段 1 仍是强触发，主动回复在阶段 2 由 F2.2/F2.3 生效）。
2. 不能变成"每条消息都回复"：普通闲聊、低信息量内容忽略。
3. 每次准备回复时建立"本轮消息边界"：以开始处理这一轮时已经收到的消息作为本轮输入；debounce 最多合并 5 条；一旦本轮开始调用模型，之后新到的消息不加入本轮上下文、也不打断当前处理；当前回复发送完成后，再处理之后的新消息。
4. 同一群同一时间只允许一个回复任务运行。
5. 新消息在当前回复任务运行期间可以先保存进数据库，但不要自动加入正在进行的模型上下文。
6. 当前回复完成后，再根据剩余新消息重新进行发言判断并处理下一轮。
7. 不要因为 Bot 正在思考，就持续创建新的模型调用。
8. 目标是"每一轮最多产生一次 Bot 回复"，而不是"每收到一条消息就回复"。

**判定顺序（程序侧，0 token；唯一实现在 `app/gate/trigger.py`）**

| 顺序 | 条件 | 结果 | 原因码 |
|---|---|---|---|
| 1 | @Bot / 回复 Bot / 命中别名 | 回应（不受冷却限制） | `mention` / `reply_to_bot` / `alias` |
| 2 | 疑问句式（`?` `？` 或疑问词） | 候选 → 过闸门 | `question` |
| 3 | 报错 / 异常 / 失败类关键词 | 候选 → 过闸门 | `troubleshoot` |
| 4 | 链接 / 文件 / 命令 / 配置类关键词 | 候选 → 过闸门 | `resource` |
| 5 | 距 Bot 上次发言 ≤ `FOLLOWUP_MAX_MESSAGES`（含本条，默认 5 条）且含承接词 | 候选 → 过闸门 | `followup` |
| 6 | 候选通过闸门 | 回应，计入冷却与窗口额度 | 上述原因码 |
| 7 | 候选被冷却或窗口上限压住 | `wait`：本轮 0 token，只入库 | `cooldown` / `quota` |
| 8 | 其余（闲聊、捧场、无信息量） | `ignore`：0 token | `not_addressed` |

- `wait` 不是"稍后自动回复"：被压住的消息只入库，等后续新消息重新触发判定。
- 闸门状态（上次主动发言时间、本窗口已用次数）按 `chat_id` 隔离，存在于进程内存中，重启后归零。
- 被点名的回应不占冷却与窗口额度：被叫到才说话不算"插话"。

### 2.2 私聊规则

1. 当前版本默认完全不处理私聊（`ALLOW_PRIVATE_CHAT=false`）。
2. 私聊不调用 LLM。
3. 私聊不调用任何工具。
4. 私聊不进入群聊记忆：不写入 `messages`，不进入任何群的上下文。
5. 私聊不产生 Token 消耗。
6. 可以保存必要的 Telegram 元数据（`updates`），但默认不生成回复。
7. 未来如果需要支持私聊，应设计为独立开关，默认关闭（开关打开时行为与群聊一致）。

### 2.3 通用输出规则

- 只输出给用户看的最终内容，不输出内部分析与"我接下来要…"。
- 能一句话回答就不写长文；不重复用户已知信息。
- 简单问题不调用工具；工具结果只用于回答当前问题，不整段转述。
- 不确定就说不确定，不为了显得有用而编造。
- 不以客服口吻每句都接话：允许完全不说话。

## 3. 已否定的方案（不要重提）

| 方案 | 否定原因 |
|---|---|
| 模型自判权限 / "拿不准就放行" | 安全边界必须在程序侧；模型只选工具，不判权限 |
| 只靠扫描 `os.system/subprocess/eval` 当沙箱 | 能绕过；扫描只作 preflight 提示 |
| 429 时整个程序睡眠 | 会阻塞所有群 |
| 第一版上向量数据库 / Redis / 微服务 / MCP | 复杂度远超收益，SQLite + FTS5 足够 |
| 第一版上 microVM / Kata / gVisor | 先做好 Docker 的严格参数再谈 |
| 整仓/整个 workspace 投喂给模型 | 上下文与成本双爆，必须按需读取 |
| 记忆"越多越聪明"（全量历史入上下文） | 成本线性上升且被噪声干扰 |
| 每条群消息都进大模型 | 闸门硬规则先行，不值得回应的 0 token |
| 面板直连 SQLite / workspace / 工具执行器 | 两套事实来源与两套权限判断，安全边界会分叉（必须经服务层） |
| 用前端隐藏按钮当权限 | 前端不在信任边界内，任何人都能直接调 API；授权只由后端判定 |
