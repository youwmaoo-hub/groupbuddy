整体上，你这套方案**方向是对的，而且已经不是“玩具 Bot”设计了**。真正需要改的，不是再堆功能，而是把“谁能让 Bot 做什么”这一层做硬。

有几个地方我会直接改：

1. **“规则拿不准就放行给模型”不要这么做。**
   模型只能决定“要不要调用哪个工具”，不能决定“这个工具有没有权限执行”。尤其是 `write_file / run_code / host_info / 出网`，必须由程序自己的权限策略判断，失败就拒绝。

2. **`run_code` 前扫描 `os.system / subprocess / eval` 远远不够。**
   这些只能算第一层提示检查。真正安全边界必须是容器/VM 本身：非 root、只读根文件系统、独立 workspace、CPU/内存/PID/文件大小限制、默认无网络、禁止访问 Docker socket、禁止宿主机目录挂载。否则有人一句话就可能让模型执行危险代码。

3. **“Bot 收不到其他 Bot 消息”现在不能再当成绝对规则。**
   Telegram 现在已经有 Bot-to-Bot Communication Mode；满足相应条件时，Bot 可以收到其他 Bot 消息。你的程序仍然可以主动 `from_user.is_bot` 过滤掉，但这是**你的产品规则**，不是平台绝对限制。([Telegram][1])

4. **限速不要写死成“整个 Bot 一旦 429 全停”。**
   Telegram 的确有单聊天约 1 条/秒、群约 20 条/分钟、批量广播约 30 条/秒等限制，但实际应该让出站队列根据 `retry_after` 做退避，而不是整个程序一起睡眠。([Telegram][2])

5. **记忆建议按“群 + Topic”考虑。**
   如果以后用了论坛主题，一个 `chat_id` 里可能存在多个完全不同的话题。最简单可以第一版只用 `chat_id`，但数据库结构预留 `thread_id`。

6. **工具最好分权限等级。**
   我会这样分：
   `L0 calc/search` → `L1 read_file` → `L2 write_file/send_sticker` → `L3 run_code` → `L4 host_info/联网高权限`。
   群主可以关闭某一级，模型永远不能自己提升权限。

# 第五阶段：实现“什么时候说话”

这是整个 Bot **最重要的产品逻辑之一**。

千万不要直接：

```python
if message:

```

你应该先做：

```text
message
   ↓
TriggerDetector
   ↓
RESPOND
IGNORE
WAIT
```

我会给它四种情况。

### A. 强触发

直接说。

```text
@Bot
回复 Bot
Bot 名字
Bot 昵称
```

---

### B. 可解释内容

直接说。

比如：

```text
这是什么？
为什么？
怎么做？
报错：
命令：
配置：
账单：
文件：
链接：
```

你这个想法是对的。

---

### C. 上下文追问

例如：

```text
用户A：DeepSeek 为什么这么贵？

Bot：因为……

用户B：那 V4.1 Flash 呢？
```

即使 B 没有点名，也应该继续回答。

这个时候不能只看当前消息。

应该检查：

```text

        ↓

        ↓
当前消息是否是它的语义延续
```

第一版甚至不需要 AI 分类。

简单规则就能解决 70%：

```text
当前消息距离 Bot 上一次回复 < N 条
且用户发言具有疑问/承接词
→ 放行
```

后面再让模型做语义判断。

但是这里还有一个你没写出来的重要东西：

## 同一个群最好只能同时处理一个 Agent Loop

否则：

```text

请求 B
请求 C
```

全部同时进入模型，就可能发生：

```text
Bot 回复 A
Bot 回复 C
Bot 回复 B
```

所以你最好做：

```text

```

逻辑是：

```text

```

不同群：

```text
群A → 可以并行
群B → 可以并行
群C → 可以并行
```

同一个群：

```text
A → B → C
严格排队
```

这比单纯的 `asyncio.gather()` 更重要。

# 第二十三阶段：出站队列

所有：

```text
sendMessage
sendSticker
editMessage
```

都不要让业务代码直接发。

全部进入：

```text
OutboundQueue
```

例如：

```text
Agent
 ↓
OutboundQueue
 ↓
RateLimiter
 ↓
Telegram API
```

然后实现：

```text
per-chat limiter
global limiter
sticker limiter
retry_after
exponential backoff
```

Telegram 官方目前的 FAQ 给出的典型限制包括：单聊天尽量不要超过 1 消息/秒、群约 20 消息/分钟、批量广播约 30 消息/秒；超过时可能返回 429。([Telegram][2])

你自己的设置可以更保守：

```text
群：
10~15/min

单聊天：
0.8~1/s

Sticker：
例如 1/20s
```

这样实际运行会舒服很多。

```text
↓

↓
```

而且最好避免把一个代码块拆坏。

# 第三十二阶段：`asyncio.gather()`

这里也不要“所有工具都并行”。

可以：

```text

+
calc
+
read_file
```

并行。

但：

```text
write_file
→
run_code
```

如果 `run_code` 要读取刚写入的文件，就必须：

```text
write_file
↓
await
↓
run_code
```

所以你应该让工具依赖关系决定是否并行，而不是：

```python
asyncio.gather(*all_tools)
```

盲目全并行。

# 最后给你一个真正适合动手的顺序

**你不要现在就做全部功能。**

你按这个顺序操作最舒服：

```text

⑤ 建项目目录

⑦ 写 .env
⑧ 写最简单的 long polling
⑨ 打印收到的群消息
⑩ 加 update_id 去重
⑪ 加消息过滤
⑫ 加 1–2 秒 debounce
⑬ 加 chat_id 队列
⑭ 接 DeepSeek API
⑮ 让 Bot 正常聊天

⑰ 做 Trigger Gate
⑱ 做 Tool Registry
⑲ 先只做 calc
⑳ 再做 search_web
㉑ 再做 read_file

㉔ 做 workspace

㉗ 做权限系统
㉘ 做 outbound queue

```

```text
+

+

+

+
```

先把这个跑起来，你已经有一个很好玩的“群聊 AI Bot”了。
