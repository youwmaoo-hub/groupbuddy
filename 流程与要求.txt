有，而且这里我会把它分成两部分：

**A. 你交给“开发 Agent”之前，要先把哪些规矩钉死。**
**B. 群宠真正跑起来以后，怎么让它少吃 Token、少烧钱。**

你这个项目最容易犯的错误其实不是“代码写错”，而是 **Agent 很勤快，结果你花了大量 Token 让它反复读文件、重写、解释、测试、贴日志**。你之前已经遇到过“几千万 Token 写游戏，最后自己没学到多少”的情况，所以这个 Bot 更应该从第一天就设计成“省 Token 开发”。

---

# 一、交给开发 Agent 之前，最应该提前说好的东西

你可以把下面这些直接写进项目根目录的：

```text
AGENTS.md
```

或者：

```text
CLAUDE.md
AGENTS.md
DEVELOPMENT.md
```

让 Agent 每次都知道。

## 1. 先规定：不要擅自扩大项目

这一句非常重要：

> 只实现当前任务要求，不主动增加功能，不引入新框架，不进行架构重构，不为了“更完善”而修改无关代码。

否则你说：

> 给 Bot 加一个 calc

Agent 很容易变成：

```text
calc
+
config 重构
+
数据库重构
+
日志系统
+
Docker 重构
+
测试框架
+
README
+
部署脚本
```

Token 直接爆炸。

---

# 2. 明确“先读，再改；只读必要文件”

让 Agent 遵守：

> 修改前先定位相关代码，只读取完成当前任务所必需的文件和代码片段，禁止无目的扫描整个项目。

最好再加：

> 不允许为了理解项目而把整个仓库、整个日志、整个数据库、整个依赖目录读进上下文。

这对省 Token 非常狠。

比如你的项目以后 20 个文件：

```text
tools/
memory/
telegram/
sandbox/
...
```

你让 Agent 改 `sticker.py`。

正确行为应该是：

```text
读 sticker.py
读 registry.py
必要时读 models.py
修改
测试
```

而不是：

```text
把 20 个文件全部 cat 出来
```

---

# 3. 明确“优先 patch，不重写整个文件”

直接告诉 Agent：

> 优先使用最小 diff 修改。除非文件结构已经无法维护，否则不得整文件重写。

这一条特别重要。

很多 Coding Agent 很喜欢：

```text
原文件 500 行
→ 重写成 700 行
```

最后你只是让它改一个函数，结果整个 Git diff 都变了。

后续你甚至不知道哪里被改坏。

---

# 4. 要求它改之前先给“内部实施计划”，但不要把计划写成小作文

可以规定：

```text
收到任务后：
1. 判断需要修改哪些文件
2. 用一句话说明方案
3. 直接实施
4. 测试
5. 最后只汇报改动和测试结果
```

不要：

> “下面我将从架构层、业务层、数据层、异常层、未来扩展层……”

这种最烧 Token。

---

# 5. 禁止重复解释已经存在的代码

加入：

> 已经明确的需求、文件结构、接口定义和前文结论，不要重复复述。

尤其是 Agent 每一轮都：

```text
你的项目是一个 Telegram Bot……
项目采用 Python……
使用 SQLite……
```

这些都是纯烧 Token。

---

# 6. 定义“完成标准”

否则 Agent 很可能一直修。

例如：

```text
任务完成标准：
- 功能实现
- 类型/语法检查通过
- 相关测试通过
- 没有新增明显错误
完成后停止，不继续优化。
```

然后加：

> 测试通过后不要继续主动重构。

这能省掉非常多无意义的迭代。

---

# 7. 明确什么时候不能碰其他模块

例如做：

```text
send_sticker
```

就规定：

> 非必要不得修改 memory、sandbox、database、Telegram handler 等模块。

形成：

```text
局部任务
↓
局部修改
↓
局部测试
```

而不是：

```text
改一个功能
↓
全项目重构
```

---

# 8. 让 Agent 使用“契约”，不要每次重新理解需求

把核心协议固定下来。

例如：

```text
docs/
├── architecture.md
├── tool_spec.md
├── database.md
└── behavior.md
```

其中：

`tool_spec.md`

固定：

```text
calc
search_web
read_file
write_file
run_code
send_sticker
host_info
```

每个工具：

```text
输入
输出
权限
超时
错误格式
```

Agent 下一次只需要：

```text
读取 tool_spec.md
```

而不是你每次重新说一遍。

---

# 9. Tool 输出必须“短而结构化”

这是以后给**群宠本身**省 Token 最有效的办法之一。

不要：

```text
search_web 返回一大坨网页正文
```

而是：

```json
{
  "title": "...",
  "url": "...",
  "snippet": "..."
}
```

最多：

```text
top 3~5
```

例如搜索工具不要给模型：

```text
10 个网站
每个 3000 字
```

只给：

```text
结果1：标题 + 150字摘要 + URL
结果2：标题 + 150字摘要 + URL
结果3：标题 + 150字摘要 + URL
```

否则工具结果本身就能吃掉大量上下文。

---

# 10. 文件工具也要限量

`read_file` 千万不要设计成：

> 给我整个文件。

而是：

```json
{
  "path": "main.py",
  "start_line": 100,
  "end_line": 150
}
```

或者：

```json
{
  "path": "main.py",
  "query": "run_code"
}
```

这样模型需要看 50 行，就别给 5000 行。

---

# 二、你这个群宠 Bot，本身最值得做的省 Token 优化

这里是重点。

---

## 妙招 1：绝对不要“每条群消息都进大模型”

你现在的：

```text
Telegram
↓
发言闸门
↓
LLM
```

是对的。

而且我建议再狠一点：

```text
明显应该回答 → 主模型
明显不该回答 → 0 Token
不确定 → 小模型/轻量判断
```

例如：

```text
哈哈哈哈
草
666
卧槽
晚安
```

这些很多时候根本没必要进大模型。

---

# 妙招 2：把“是否该回复”尽量变成程序规则

例如：

```text
@Bot             → 回复
回复 Bot          → 回复
Bot 名字          → 回复
问题句式          → 倾向回复
明显接着 Bot      → 回复
纯闲聊            → 默认不回复
```

而不是：

```text
每条消息：
“你觉得我应该不应该回复？”
```

因为你为了省主模型 Token，结果每条消息又调用一次“小模型”，可能只是换了一个地方烧钱。

---

# 妙招 3：Debounce 是省钱神器

你已经设计了：

```text
1～2秒
最多5条
```

这个一定要保留。

例如：

```text
“你”
“知道”
“这个吗”
“？”
```

原本：

```text
4 次请求
```

合并以后：

```text
1 次请求
```

群里尤其有效。

---

# 妙招 4：不要每轮都塞“最近 50 条完整消息”

你原来的：

```text
最近30~50条
```

可以保留，但不要永远固定塞满。

可以动态：

```text
普通问题 → 最近 15~20 条
复杂问题 → 最近 30~50 条
代码任务 → 相关消息 + 必要历史
```

例如：

```text
“哈哈”
```

根本没必要带 50 条。

而：

```text
“继续刚才那个代码问题”
```

才需要更完整上下文。

---

# 妙招 5：短期记忆不要塞太多“无价值消息”

例如：

```text
A：哈哈
B：草
C：666
D：笑死
E：确实
```

这些留在数据库没问题，但**没必要每次送给模型**。

上下文应该区分：

```text
原文存储
≠
模型上下文
```

这是一个非常关键的思想。

SQLite 可以保存很多东西。

模型只看：

```text
有用的
```

---

# 妙招 6：摘要一定要压缩

你的摘要不要写成：

> 2026年10月6日下午，群里的 Alex 提到了……然后 B 用户说……随后……

应该直接：

```text
当前项目：
Telegram 群宠 Bot。

用户正在：
测试 DeepSeek API。

已完成：
Bot 收消息、去重、debounce。

待完成：
Tool Calling、Sticker。

偏好：
希望省 Token。
```

这比流水账省得多。

---

# 妙招 7：普通问题和复杂问题用不同模型档位

这是非常适合你这个项目的。

例如：

```text
简单：
“2+2”
“你好”
“Python 是什么”
        ↓
Flash

复杂：
“帮我分析这个项目架构”
“改这个代码”
“调试 Docker”
        ↓
更强模型
```

不要所有消息都用最贵/最强模型。

甚至可以：

```text
Flash
 ↓
判断复杂度
 ↓
简单 → Flash
复杂 → Pro
```

不过注意：**路由模型本身也消耗 Token**，所以只有在复杂请求比例不低时才值得这么做。

---

# 妙招 8：工具循环不要死守 4 轮

你现在：

```text
最多 4 轮
```

很好做安全上限，但实际上可以：

```text
普通聊天：0轮
简单工具：1轮
复杂任务：最多2轮
代码调试：最多4轮
```

不要所有请求都允许 4 次。

---

# 妙招 9：工具失败不要把整坨错误扔给模型

你已经设计：

```json
{
  "error": "timeout",
  "tool": "search"
}
```

这个非常好。

保持：

```text
小
结构化
机器可读
```

不要把：

```text
5000 行 Docker traceback
```

全部送进去。

可以：

```json
{
  "error": "timeout",
  "tool": "run_code",
  "message": "execution exceeded 20s"
}
```

必要时再让模型请求：

```text
“查看错误详情”
```

---

# 妙招 10：代码工具输出必须截断

这是我特别建议你加的。

用户：

> 跑一下这个程序。

结果可能：

```text
打印 300 万行
```

千万不要原样塞模型。

设置：

```text
stdout 最大 8KB
stderr 最大 8KB
```

超过：

```text
[output truncated: 2.7MB]
```

否则一个程序能把你的上下文直接吃爆。

---

# 妙招 11：搜索结果限制长度

例如：

```text
search_web
top_k = 5
snippet <= 500 chars
```

而不是：

```text
top_k = 20
全文
```

模型通常不需要看那么多。

---

# 妙招 12：不要把整个 workspace 自动塞进去

千万不要：

```text
用户：
“修改 main.py”

→ 把 workspace 里 200 个文件全给模型
```

正确：

```text
用户：
“修改 main.py”

↓
打开 main.py
↓
发现 import utils
↓
只打开相关 utils
```

这就是所谓的：

**按需检索，而不是整个工作区投喂。**

---

# 妙招 13：固定 Prompt 尽量固定在前面

结构：

```text
[固定]
人设
群设定
工具定义

[动态]
最近消息
摘要
检索结果
当前用户问题
```

不要把一些会变化的东西插来插去。

这样以后如果你用的模型/服务支持提示词缓存，会更容易吃到缓存收益。

---

# 妙招 14：模型不要反复“自言自语”

系统提示里明确：

```text
只输出最终需要给用户看的内容。
不要输出内部分析。
工具调用期间不要解释内部过程。
```

这样：

```text
“让我想一下……”
“我现在将……”
“接下来我要……”
```

这种无意义输出会少很多。

---

# 妙招 15：让 Bot 知道什么时候“一个字都不用说”

这是非常适合群宠的。

例如：

```json
{
  "action": "ignore"
}
```

或者内部：

```text
NO_REPLY
```

所以：

```text
有人说：
“哈哈哈哈”
```

模型可以决定：

```text
ignore
```

而不是强行：

> 哈哈哈哈哈哈确实😂

这样你的 Bot 会显得更像“群友”，而不是“每句话都接的客服”。

---

# 三、还有一个很重要：把“使用者 Token”和“开发 Token”分开管理

我非常建议你从第一天就区分：

```text
Developer Token
```

和：

```text
Bot Runtime Token
```

例如：

```text
开发阶段：
Agent → API
```

和：

```text
实际运行：
Telegram Bot → API
```

不要混在一起。

因为你以后会发现：

```text
改一次代码
```

可能要花：

```text
几十万 Token
```

而真正 Bot 运行可能：

```text
一天几百万 Token
```

两个成本完全不同。

---

# 四、我最推荐你给 Coding Agent 的总规则

你甚至可以直接把这段丢给你的 Agent：

```text
开发规则：

1. 只实现当前任务，不主动扩展功能。
2. 修改前先定位相关文件，只读取必要内容，不扫描整个仓库。
3. 优先最小 diff，不整文件重写。
4. 不修改与当前任务无关的模块。
5. 已确定的需求、架构和接口不要重复解释。
6. 优先复用已有代码和依赖，不随意引入新框架。
7. 完成功能后立即运行针对性测试，不做无关重构。
8. 测试通过后停止，不继续自行优化。
9. 终端输出、日志、搜索结果只读取必要范围，禁止把大量无关输出放入上下文。
10. 工具接口、数据库结构、权限策略属于契约，未经要求不得擅自修改。
11. 安全边界必须由程序实现，不能把权限判断交给模型。
12. 文件访问必须限制在 workspace。
13. run_code 必须经过 sandbox，禁止宿主机直接执行。
14. 任何 API Key、Bot Token、环境变量、隐私数据不得写入日志。
15. 每次任务最后只汇报：修改了什么、测试了什么、结果如何、还有什么已知问题。
```

这段我觉得你应该直接保存。

---

# 五、而你的群宠 System Prompt，也应该提前规定“省钱模式”

例如：

```text
你是这个 Telegram 群里的 AI 群宠。

行为：
- 只有值得回复时才回复。
- 被点名、被回复、明确的问题、报错、命令、配置、文件、链接、怎么、为什么、是什么等优先回答。
- 对没有信息量的纯捧场可以忽略。
- 用户连续追问上一条内容时，即使没有再次点名，也继续接话。
- 不重复用户已经知道的信息。
- 能用一句话回答时不要写长文。
- 简单问题不要调用工具。
- 只有确实需要时才使用工具。
- 工具结果只用于回答当前问题，不要重复转述完整工具输出。
- 不确定时说明不确定，不为了显得有用而胡编。
- 代码、文件、搜索结果按需读取，不主动读取无关内容。
```

这比：

> “你是一个超级聪明的 AI，要热情地帮助所有人……”

省钱得多，而且更适合群宠。

---

# 六、你的 Bot 我甚至建议做成“四档省 Token 模式”

以后群主可以：

```text
/mode economy
/mode normal
/mode smart
/mode unrestricted
```

### Economy

```text
少回复
短上下文
低输出上限
少工具
不主动贴纸
```

### Normal

正常群宠。

### Smart

```text
长上下文
更多工具
复杂问题更愿意处理
```

### Unrestricted

测试模式。

这样你自己玩 Bot 的时候，不用每次改代码。

---

# 七、还有一个你很容易忽略的省钱点：不要让 Bot “过度有记忆”

很多人做 AI Agent 会觉得：

> 记得越多越聪明。

实际上：

```text
记忆越多
→ context 越长
→ Token 越多
→ 模型越容易被垃圾信息干扰
```

你的设计应该是：

```text
原始历史
      ↓
SQLite 永久保存
      ↓
     摘要
      ↓
重要事实 / 项目状态
      ↓
真正需要时检索
```

而不是：

```text
过去所有聊天
↓↓↓↓↓↓
全部塞给模型
```

---

# 八、从“你以后每天使用 Bot”的角度，我最推荐的最终省 Token 策略

实际上可以浓缩成这一条链：

```text
群消息
 ↓
程序硬规则
 ↓
不值得回复 → 0 Token
 ↓
值得回复
 ↓
1~2秒 debounce
 ↓
动态选择 10~50 条上下文
 ↓
先便宜模型 / 简单路径
 ↓
只有复杂问题进入强模型
 ↓
工具按需调用
 ↓
工具结果严格截断
 ↓
最多 1~2 轮
 ↓
最终短回答
```

这样和“每条消息都塞 50 条历史 + 所有工具 + 强模型 + 4 轮 Agent”相比，成本差距会非常大。

---

## 最关键的其实就 5 条

你可以直接记成：

> **不该说的话不进模型。**
> **不需要看的内容不进上下文。**
> **不需要用的工具不调用。**
> **不需要继续思考就立刻结束。**
> **Agent 改代码只做最小 diff。**

这五条既能省你开发阶段给 Coding Agent 的 Token，也能省你之后群宠真正运行时的 Token。

而且你这个项目特别适合做成一种 **“会主动参与群聊，但不会像客服一样每句话都插嘴”** 的群宠，这实际上比单纯堆模型能力更重要。
